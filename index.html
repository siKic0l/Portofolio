Software Engineer — from requirements to release

Open to Quality Assurance • Project / Delivery • Software Engineering roles

I’m an Informatics graduate who ships software end to end. Every system I’ve delivered started the same way — working out with the client what they actually needed — and finished the same way: deployed, verified, and handed over to the people who use it every day.

At BLAST ID I was the solo IT developer. That meant building a bilingual company profile site, a Warehouse Management System with inventory tracking and asset lending, and Electron-based arcade software run live at events — with Next.js, React, TypeScript, Tailwind CSS, and Supabase (PostgreSQL). It also meant everything around the code: scoping requirements with stakeholders, deciding what shipped first, handling deployment, and training the staff who now depend on it.

I test what I build. Every release went out with regression checks and verification against what was promised. I took that further on my own with two full manual testing cycles — the OrangeHRM HRMS and the Restful Booker API — 221 test cases and 11 defect reports, scoped and prioritized upfront, then executed and tracked in Qase.io with Postman for the API work.

Requirements, building, testing, release — I’ve owned all four, just at the scale of one person rather than a team. That’s why Quality Assurance, Project Delivery, and Software Engineering all make sense to me as a next step: they’re different entry points into work I already do. The scale is what I’m after. Wherever I start, I’d rather be the one asking what “done” actually means before the first line gets written.

How I Work

The same four steps on every project, whether what ships is a client website or a test suite.

1

Understand the need

BLAST ID served brands from Djarum to regional banks, but its event portfolio was scattered across social media — prospective clients had nowhere to check the company's track record before making contact. Every case study here opens with the client's three core requirements, not a tech stack.

Read the BLAST ID case study →
2

Decide what ships first

Eight Restful Booker endpoints, grouped into seven suites, with priority agreed before a single test ran — authentication and write operations classed as critical. Knowing what matters most is what makes a plan survive contact with a deadline.

See how it was scoped →
3

Build it, then try to break it

Across a web HRMS and a REST API: 221 test cases and 11 defect reports, each written with reproduction steps, expected versus actual results, and impact. Two cases were recorded as Blocked rather than forced into a pass or fail, because the difference changes what happens next.

See the testing work →
4

Hand it over properly

The Warehouse Management System is used by warehouse staff every day, so shipping it meant more than a Vercel deployment — it meant training the people who would depend on it and leaving documentation they could actually use.
